Release: **$ARGUMENTS** (no version given: the milestone that is done). You are the Lead. The owner approves twice here: the milestone (`demo`) and the release. Run each check yourself and show the owner only what is missing (rule "Asking for an approval").

1. **Ready?** Every issue of the milestone closed through `/cb-build done` (or moved to the next one with a note); every merged PR with its level, its reviews and a valid PASS; with Test, `docs/tech/test-cases/` covers every requirement the milestone delivers; the SRS and `CHANGELOG.md` "Unreleased" current. If not, report what is missing and stop.
2. **Staging:** merge `dev` into `staging`. Ask the Dev (rule "Hand-offs", prompt `Build staging for v<X.Y.Z>.`) for `node scripts/ci-local.mjs staging --full` (every step, once per milestone) and the `staging` image (`node scripts/run.mjs staging`, or `/cb-deploy staging <tag>` when a staging server is set); with CI on GitHub the `:staging` image is built there. Ask for the regression on `staging` (Test, or the Dev without Test; prompt: `Run the regression for v<X.Y.Z> on staging.`), with the update and rollback scripts on the staging database when the milestone changes data (rule "Data changes"). Then the acceptance: every acceptance criterion of the milestone's stories and CRs tried on `staging` (in the browser for a product with screens, desktop and about 390 px wide), each result in the acceptance section of `docs/tech/test-reports/<version>.md`, a defect for each failure (Test after its regression, prompt `Accept v<X.Y.Z> on staging.`; without Test, you). Copy the results into section 1 of `docs/product/handover/<version>.md` and pick 3-5 of them as the owner's scenarios. A defect is fixed on `dev` and merged into `staging` again; then only the affected area and the main journeys are tested again.
3. **The milestone approval:** give the owner the link (or the one command that starts `staging`) and the 3-5 scenarios in plain words (steps, expected result, one example of a wrong result; with screens one at about 390 px wide), with the `For you` block. Wait for "All pass" or the failures; turn each failure into a defect and fix it as in step 2.
4. **`/cb-release demo` stops here:** report the image tag and the link or command to show the client. Nothing is tagged. A later `/cb-release` of the same milestone skips steps 2 and 3 when nothing reached `staging` since.
5. **`/cb-release`:** finish the handover (`docs/product/handover/<version>.md`, template `handover.md`: delivered, changes, what the client must prepare, accepted risks, how to roll back, sign-off). Copy the tasks' actual AI times into the milestone file and `docs/ai-log.md`. Run `node scripts/release.mjs --write` (it handles both line endings and warns if the changelog was not updated), write `docs/releases/<version>.md`, update `CHANGELOG.md`, the SRS revision row and the Stage line in `CLAUDE.md`. **The release approval:** what is missing, if anything; the `For you` block (what will be published, the regression and the acceptance on `staging`, the scenarios the owner passed, the evidence: CI, tests, image; open risks; the handover to send the client); then the question.
6. **After "Approved", no new tests:** merge into `main` exactly the `staging` commit that was accepted (nothing else reached `staging` since), tag, `git push origin main <version>`, `gh release create`. Ask the Dev for the release image and its start check (`node scripts/run.mjs <version>`: with CI on this machine it tags the accepted `staging` image when the files are the same, and builds only when they differ; on GitHub the tag builds `ghcr.io/<owner>/<repo>-app:<version>` with its SBOM). Report in a few lines the image and that command. Then the end of the phase (rule "Fresh context"): write where things stand in the next milestone file and clear your own context, then `/cb-plan` the next milestone. If the release fails in production, roll back to the previous tag (`node scripts/run.mjs <previous version>`, plus the rollback script when data changed) with the owner's OK.
