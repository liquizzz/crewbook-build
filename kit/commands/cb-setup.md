description: Set up the project in ten steps (tools, the idea with roles and autonomy, requirements, stack, look and feel, GitHub, environments, the plan approval, worktrees, sessions); run it again to go on where it stopped
---

Set up this Crewbook project. You are the Lead (check `.claude/role`; if not, say which session to open and stop). Until setup is done the other sessions wait.

**How to ask.** Each step comes with a default or a proposal the owner can take as it is. Understand what the owner means, fill the gaps, suggest as much as is useful; never ask round after round. Inside a step ask at most one short round (three questions at most, each with your suggested answer). Use the app's question tool where it has one (a multi-select for the roles). Only step 8 is an approval: everything before it is a draft the owner reads and corrects, never a separate sign-off. Talk to the owner in the language of their first message: if it is not the one in `.claude/project.json`, set `language` there and the Language line of `CLAUDE.md` (`node -e` with `languageLine` from `scripts/project-level.mjs`, or edit the line), and rewrite `START-HERE.md` in that language at the end (commands, paths, links and session names stay in English).

**Where it stopped.** `node scripts/setup-state.mjs` lists the steps and the next one. A step is done only when `node scripts/setup-state.mjs done <step>` accepted it, after its own check, never because a file exists: a step that stopped halfway runs again from its start. Run again, `/cb-setup` goes on from the next step.

1. **Tools** (`tools`). Check your own skill list for `superpowers:`, `product-management:`, `code-review` and `context7`. If any is missing, run `node scripts/plugins.mjs`, tell the owner to type `/reload-plugins` and then `/cb-setup` again, and stop. In Claude Code desktop: rename your session "<Project> - Lead" if needed (`set_session_title`), and put it in a sidebar group named after the project (`create_group`, then `move_sessions` with `self`). Then `done tools`.
2. **The idea, the roles and the autonomy** (`idea`), in your first message to the owner, so they answer all three in one reply:
   - the idea in their own words (or a document, a product to copy, an old system);
   - the roles: the table from `node scripts/roles.mjs`. The Lead and the Dev are always on; UI/UX, Frontend and Test are ticked by default. Say in one line who takes the work of a role left out (the Lead designs; the Dev builds both layers; the Dev tests and the Lead accepts);
   - the autonomy: the four settings with their defaults, each in one line: `relay` on (sessions send each other their hand-offs), `merge` all (the levels the Lead merges by itself: off, only-L0, up-to-L1, up-to-L2, all), `escalate` on (a stuck task moves one step up the model ladder below Opus), `testing` off (Test checks each merged task; only with Test).

   Apply them: `node scripts/roles.mjs set <the chosen optional roles, or none>`, `node scripts/crew-settings.mjs <setting> <value>` for each, then `node scripts/setup-state.mjs done idea --autonomy "<the owner's answer, in a few words>"`.
3. **Requirements** (`requirements`; `product-management:write-spec`, `product-brainstorming`; Skills table). One short round on what only the owner knows (who uses it, the problem, what this first stage does, how it is accepted), then the first draft at once, in the kit's documents: the stories (`docs/product/stories/`), the stories usually missing for this kind of product as suggestions the owner keeps or drops, and the function tree (`docs/product/function-tree.md`: modules, then screens or functions, then the main actions). Mark each guess ⚠️. Show it as a draft: "read it and tell me what to change; you approve everything together in step 8". Put corrections straight in, then `done requirements`.
4. **Deployment model and stack** (`stack`; `superpowers:brainstorming`, from the requirements; no second requirements document). One round on scale (users, how many at once, data volume, where it runs, the hosting budget, a stack the owner or the client requires), then three architectures side by side: the stack, the hosting, the running cost, what fits and what does not, one marked as recommended. The owner picks, asks for a change, or says "you decide" (then take the recommended one and say why in one line). Write `docs/tech/solution-design.md` from it (lead.md, Work 3), then `done stack`.
5. **The look and feel** (`design`), only when the product has screens; otherwise `done design --no-screens`. You prepare it yourself here, whether or not the project has UI/UX: its session opens only after the plan. With `ui-ux-pro-max`, search the styles, palettes and font pairs that fit the product and its users; show 2-3 named directions side by side in `design/look-and-feel.html`, each applied to the main screen, at desktop and phone width (rule "Show finished work only"). The owner picks one by its name; that is a choice for the plan, not an approval. UI/UX, when the project has it, takes the chosen direction over in its first design round. Then `done design`.
6. **GitHub** (`github`). `node scripts/connect-github.mjs --check`. When the project is not connected (init ran with "GitHub: none"), ask the owner once for the repository name and visibility (suggest `<their GitHub user>/<project>`, private): creating it is an account action. On yes, `node scripts/connect-github.mjs <owner/name> <private|public>` (repo, branches pushed, labels, Dependabot, the board, where CI runs, `"repo"` in `.claude/project.json`). Then `done github`. Nothing later in the setup (milestones, pushes, Actions) runs before this step.
7. **Environments** (`environments`; `/cb-env setup`). Record what the stack uses (`node scripts/db-setup.mjs use database <postgres|mssql|none>`, `use cache <redis|none>`), then, without asking, `node scripts/db-setup.mjs local`: the database and the cache run in the project's own Docker with one account each. Only when the owner says the project uses servers they already have, they run `node scripts/db-setup.mjs connect database` (or `cache`) in a terminal instead. Fill the migrate and seed commands, then `create`, `check` and `reset-check`. Propose the build host, the registry and `staging` too. Write `docs/tech/ops/environments.md`. `done environments` checks that every service has its project account, the databases exist and `check` passes; a project without a database or cache passes `--no-database`. A run again keeps everything already set up: no new container, no new password, no reset.
8. **The plan approval** (`plan`). One page in the chat, with links: what the product does and for whom, the stories, the function tree, the architecture and stack, the look and feel picked, the environments, the first milestone (its scope and AI time), the roles and the autonomy, and the open decisions. Ask once: approve, or say what to change. Ask this alone, never in the same message as another choice: an answer counts as the plan approval only when it says so ("Approved", "approve the plan"). An answer that picks an option and approves nothing gets the plan question again, with the option put in. On approval:
   - fill in `CLAUDE.md`: the description, the Stack line, the commands, Stage ("Delivery, milestone v0.1.0"); the design plugins in `.claude/settings.json` when the product has screens; `.claude/ownership.json` with each role's folders;
   - create milestone v0.1.0 on GitHub; set `"setup": true` in `.claude/project.json`; `done plan`; commit, merge into `dev`, push.
9. **Worktrees** (`worktrees`). `node scripts/roles.mjs worktrees --json` creates every chosen role's worktree from the committed setup, gives each its plugins, its port and, when the databases exist, its connection strings with its own `DATABASE_URL` (it runs `db-setup.mjs env`). Then `done worktrees`.
10. **Sessions and the first milestone** (`sessions`). Check each role is ready: its worktree is on `role/<role>` with `.claude/role`, and its `.env.local` has its `DATABASE_URL` when the project has a database (a yes or no from a script, never the value). In Claude Code desktop, the owner's answers to the setup are the go-ahead: for each role except yours, `start_session` with `cwd` its folder, `use_worktree: false`, the title "<Project> - <Role>", `model` Sonnet and `effort` low (you set each task's model before you send it), and the first message `Ready; wait for the Lead's task.`; then `detach_session` and `move_sessions` into your group (rule "Opening sessions" in `CLAUDE.md`). Without the app, list each folder and the session name for the owner to open. In the `deepseek` mode (rule "Models") the Dev, Frontend and Test sessions start with `claude` in their folders, in a terminal: give the owner those commands instead. Check live state: `gh run list --limit 3`; on a public repo with no run yet, tell the owner to open the Actions tab once and click "Enable Actions on this repository". `done sessions`. Report in a few lines: the roles and their sessions, the autonomy, the first milestone, links. Then start `/cb-plan v0.1.0`.
