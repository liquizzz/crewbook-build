description: Set up the project in five questions (roles, autonomy, requirements, stack, environments), get the plan approved and create every session; run it again to go on where it stopped
---

Set up this Crewbook project. You are the Lead (check `.claude/role`; if not, say which session to open and stop). Until setup is done the other sessions wait.

**How to ask.** Five questions, one at a time, each with a default or a proposal the owner can take as it is. Understand what the owner means, fill the gaps, suggest as much as is useful; never ask round after round. Inside a question ask at most one short round (three questions at most, each with your suggested answer). Use the app's question tool where it has one (a multi-select for the roles). Talk to the owner in the language of their first message: if it is not the one in `.claude/project.json`, set `language` there and the Language line of `CLAUDE.md` (`node -e` with `languageLine` from `scripts/project-level.mjs`, or edit the line), and rewrite `START-HERE.md` in that language at the end (commands, paths, links and session names stay in English).

**Where it stopped.** Run again, it goes on from the first step not done: roles (`"roles"` in `.claude/project.json`), autonomy (`node scripts/crew-settings.mjs status` shows it was set at setup), requirements (`docs/product/function-tree.md`), stack (`docs/tech/solution-design.md`), environments (`docs/tech/ops/environments.md`), the plan approval (`"setup": true`), the sessions.

0. **Plugins first:** check your own skill list for `superpowers:`, `product-management:`, `code-review`, `claude-mem` and `context7`. If any is missing, run `node scripts/plugins.mjs`, tell the owner to type `/reload-plugins` and then `/cb-setup` again, and stop. In Claude Code desktop: rename your session "<Project> - Lead" if needed (`set_session_title`), and put it in a sidebar group named after the project (`create_group`, then `move_sessions` with `self`).
1. **Roles.** Show the table from `node scripts/roles.mjs` (what each role does and when it is worth having). The Lead and the Dev are always on; UI/UX, Frontend and Test are ticked by default. Say in one line who takes the work of a role left out (the Lead designs; the Dev builds both layers; the Dev tests and you accept). Then `node scripts/roles.mjs set <the chosen optional roles, or none>`.
2. **Autonomy.** The four settings with their defaults, each in one line: the sessions send each other their hand-offs (`relay`, on); the merges you do by yourself (`merge`, all levels: off, only-L0, up-to-L1, up-to-L2, or all; empty means all); a stuck task moves one step up the model ladder below Opus (`escalate`, on); Test checks each merged task (`testing`, off, only with Test). Apply the answer with `node scripts/crew-settings.mjs <setting> <value>` for each.
3. **Requirements** (`product-management:write-spec`, `product-brainstorming`; Skills table). Ask the owner to describe the idea in their own words (or point at a document, a product to copy, an old system). Then one short round on what only the owner knows (who uses it, the problem, what this first stage does, how it is accepted), then the first draft at once, in the kit's documents: the stories (`docs/product/stories/`), the stories usually missing for this kind of product as suggestions the owner keeps or drops, and the function tree (`docs/product/function-tree.md`: modules, then screens or functions, then the main actions). Mark each guess ⚠️. Show it and ask once: approve, or say what to change.
4. **Deployment model and stack** (`superpowers:brainstorming`, from the approved requirements; no second requirements document). One round on scale (users, how many at once, data volume, where it runs, budget, a stack the owner or the client requires), then three architectures side by side: the stack, the hosting, the running cost, what fits and what does not, one marked as recommended. The owner picks, asks for a change, or says "you decide" (then take the recommended one and say why in one line). Write `docs/tech/solution-design.md` from it (lead.md, Work 3).
5. **Environments.** Propose, without asking first: the databases (the project's own and `staging`, on the shared database server of this machine when `~/.crewbook/hosts.json` lists one, else a container here), the build host and the registry (the shared ones, else this machine and GHCR), `staging` (on this machine, or a server the owner names). The owner accepts or says what to change. Write `docs/tech/ops/environments.md`; create the databases and check that a reset works.
6. **The plan approval.** One page in the chat, with links: what the product does and for whom, the stories, the function tree, the architecture and stack, the environments, the first milestone (its scope and AI time), the roles and the autonomy, and the open decisions. Ask once: approve, or say what to change. On approval:
   - fill in `CLAUDE.md`: the description, the Stack line, the commands, Stage ("Delivery, milestone v0.1.0"); the design plugins in `.claude/settings.json` when the product has screens; `.claude/ownership.json` with each role's folders;
   - create milestone v0.1.0 on GitHub; set `"setup": true` in `.claude/project.json`; commit, merge into `dev`, push.
7. **The sessions.** `node scripts/roles.mjs worktrees --json` creates every chosen role's worktree and lists them. In Claude Code desktop, the owner's answers to the setup are the go-ahead: for each role except yours, `start_session` with `cwd` its folder, `use_worktree: false`, the title "<Project> - <Role>", `model` Sonnet and `effort` low (you set each task's model before you send it), and the first message `Ready; wait for the Lead's task.`; then `detach_session` and `move_sessions` into your group (rule "Opening sessions" in `CLAUDE.md`). Without the app, list each folder and the session name for the owner to open. In the `deepseek` mode (rule "Models") the Dev, Frontend and Test sessions start with `claude` in their folders, in a terminal: give the owner those commands instead of opening them from the app.
8. Check live state: `gh run list --limit 3`; on a public repo with no run yet, tell the owner to open the Actions tab once and click "Enable Actions on this repository". Report in a few lines: the roles and their sessions, the autonomy, the first milestone, links. Then start `/cb-plan v0.1.0`.
