---
description: The environments: the project's database environment (existing or managed), its databases and their URLs, the machine's hosts and other shared services, a reset, staging backups and restores
argument-hint: "[show | setup | reset <db> | backup | restore [file]]"
---

Environments: **$ARGUMENTS** (no argument: `show`). The Lead and the Dev run this (rule "Environments" in `CLAUDE.md`). Never print a password or a connection string. The commands that take a secret or change a server are the owner's, in a terminal; give the owner the command.

- **show:** `node scripts/db-setup.mjs status` (the kind of environment, the project account, the databases, where they were checked, an old model to move) and `node scripts/hosts.mjs` (the build host, the registry, staging, the other shared services). Report in a few lines what is ready and what is missing.
- **setup** (the Lead at `/cb-setup`, step "environments", after the stack):
  1. Offer the two kinds, with your recommendation: **"I have an environment"** (a server online, on this machine or behind NAT: the owner runs `node scripts/db-setup.mjs connect` and pastes the connection string, hidden) or **"Crewbook creates one for this project"** (the owner runs `node scripts/db-setup.mjs managed create`: Docker on this machine today; another host or a native install is reported as not supported yet and the step stays not done). Do not ask "online or local" as a third kind. The connection string is the address the app really reaches: behind NAT, the mapped address and port; never assume `localhost:5432`.
  2. `connect` with an admin: one project account is created (`CREATEDB`, no other rights) and owns every database; the admin stays in the main checkout only. With an account that may create databases: it is the project account and no login is created. With less: the owner is told what is missing; nothing is stored, nothing is changed, the step stays not done.
  3. Fill `"database"` in `.claude/project.json` with the stack's `migrate` and `seed` commands (and `migrateInImage`, the migrate command inside the backend image, for `devMigrate` and `stagingMigrate`; `"shadow": true` when the stack needs a shadow database). `node scripts/db-setup.mjs --plan` lists the databases: `<project>_dev`, `<project>_frontend` and `<project>_test` (with those roles), `<project>_staging`, the CI databases `<project>_ci_*` (created and dropped by each run), and for a migration project `<project>_source` and `<project>_migration`.
  4. `node scripts/db-setup.mjs create`: every database, owned by the project account, and each checkout's URLs (each role's `DATABASE_URL` is its own database). It refuses a database or login of the same name that is not this project's. Then `node scripts/db-setup.mjs check` from this machine; the app's containers, a build host and a staging server are checked where they run, and stay "pending" until then. `node scripts/db-setup.mjs reset-check` proves a reset on a scratch database made for it, never on a database that holds data.
  5. `docs/tech/ops/environments.md` from the template.
- **reset <db>:** `node scripts/db-setup.mjs reset <db>` (drop, create, migrate, seed small); only this project's databases; `staging` needs a backup first and `--confirm`; never production.
- **backup / restore:** `node scripts/db-setup.mjs backup` (staging; keeps the last three and the pre-release one) and `restore <file> [db]` (restored by the project account, which owns every object). They use `pg_dump` and `pg_restore` when installed, else a PostgreSQL image through Docker. Once a milestone, restore one backup on the scratch database to prove it works, and note it in the test report.
- **Another project on a managed server:** the owner prints the admin with `node scripts/db-setup.mjs admin-url` in this project's terminal and pastes it into the other project's `connect`, or gives the other project an account that may create databases. The other project never starts, stops or changes this server; stopping or deleting it (`managed down` / `destroy`, with `--confirm`) names the other projects first.
- **An old project** (one login per role on the machine's shared server): `db-setup.mjs status` says so. After a backup, the owner runs `connect` with that server's admin, then `node scripts/db-setup.mjs adopt-legacy`: the databases and their objects move to one project account, the data stays, and the old logins are kept until the owner drops them once the app, the migrations and CI work.
