---
description: The environments: the project's database and cache (local in its own Docker by default, or a server the owner already has), their accounts and URLs, a reset, staging backups and restores
argument-hint: "[show | setup | reset <db> | backup | restore [file]]"
---

Environments: **$ARGUMENTS** (no argument: `show`). The Lead and the Dev run this (rule "Environments" in `CLAUDE.md`). Never print a password or a connection string. The commands that take a secret or change a server are the owner's, in a terminal; give the owner the command.

- **show:** `node scripts/db-setup.mjs status` (each service, its mode, its project account, the databases, where they were checked, an old model to move) and `node scripts/hosts.mjs` (the build host, the registry, staging). Report in a few lines what is ready and what is missing.
- **setup** (the Lead at `/cb-setup`, step "environments", after the stack):
  1. Record what the stack uses: `node scripts/db-setup.mjs use database <postgres|mssql|none>` and `use cache <redis|none>`. For a SQL Server stack, `"urlFormat"` under `"services"."database"` in `.claude/project.json` is `"ado"` (the default, an ADO.NET string) or `"url"`.
  2. The default, without asking: `node scripts/db-setup.mjs local`. Every service runs in the project's own Docker, with a project account each, passwords generated and never shown.
  3. Only when the owner says the project uses a server they already have: the owner runs `node scripts/db-setup.mjs connect database` (or `cache`) in a terminal and pastes the connection string, hidden; the address is the one the app really reaches. With an admin, Crewbook creates the one project account; with an account that may already create databases (Redis: any account), it is used as it is; with less, the owner is told what is missing and nothing changes. SQL Server needs `sqlcmd` here: ask the owner's OK to install it (`winget install sqlcmd`, `brew install sqlcmd`).
  4. Fill the stack's `migrate` and `seed` commands under `"services"."database"` (`migrateInImage` for `devMigrate` and `stagingMigrate`; `"shadow": true` when the stack needs a shadow database). `node scripts/db-setup.mjs --plan` lists the databases: `<project>_dev`, `<project>_frontend` and `<project>_test` (with those roles), `<project>_staging`, the CI databases `<project>_ci_*`, and for a migration project `<project>_source` and `<project>_migration`.
  5. `node scripts/db-setup.mjs create`: every database, owned by the project account, and each checkout's URLs (each role's `DATABASE_URL` is its own database, its `REDIS_PREFIX` its own keys). Then `check` and `reset-check` (a reset proved on a scratch database made for it, never on one that holds data).
  6. `docs/tech/ops/environments.md` from the template.
- **reset <db>:** `node scripts/db-setup.mjs reset <db>` (drop, create, migrate, seed small); only this project's databases; `staging` needs a backup first and `--confirm`; never production.
- **backup / restore** (PostgreSQL): `node scripts/db-setup.mjs backup` (staging; keeps the last three and the pre-release one) and `restore <file> [db]` (restored by the project account, which owns every object). SQL Server: the server's own BACKUP and RESTORE.
- **stop the local services:** `node scripts/db-setup.mjs local stop` (the data stays); deleting their data is the owner's (`local destroy --confirm`). They use `pg_dump` and `pg_restore` when installed, else a PostgreSQL image through Docker. Once a milestone, restore one backup on the scratch database to prove it works, and note it in the test report.
- **An old project** (one login per role on the machine's shared server): `db-setup.mjs status` says so. After a backup, the owner runs `connect database` with that server's admin, then `node scripts/db-setup.mjs adopt-legacy`: the databases and their objects move to one project account, the data stays, and the old logins are kept until the owner drops them once the app, the migrations and CI work.
